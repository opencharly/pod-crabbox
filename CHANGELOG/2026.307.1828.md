# 2026.307.1828 — fix(ci): chain the image build off tag-on-merge, not push:tags

## Summary

**Head `9674c1715d6674a67049793705d4ef8f96734240` — 1 file, +54/−10.** The image caller stops listening on a trigger that can never fire and chains off the one whose delivery is proven.

**The defect.** This repo merged and tagged — `v2026.307.1759` at `1b9a9c061755f69f3d98310b3f3896b8184ecd49` — and **no image run was created**. Every `image` run on record is `pull_request`:

```
$ gh api repos/opencharly/pod-crabbox/actions/runs?per_page=15 --jq '…event…'
tag-on-merge        | push          | main
tag-on-merge        | workflow_run  | main
charly/pr-validator | pull_request  | feat/base-image-v2
image               | pull_request  | feat/base-image-v2
…
```

**The mechanism is documented in the org's own working workflow**, `charly/.github/workflows/release-binary.yml`:

> *"tag-on-merge creates release tags via the REST API (`git.createRef`), which does NOT emit a push event … so `push: tags` / `push: branches` alone never fire for merged PRs … This workflow chains off tag-on-merge completion (`workflow_run` — the ONE trigger whose event delivery is proven)."*

It is not a token problem; GitHub's docs are explicit that an App/PAT token fires events. It is `git.createRef` emitting no push event at all. `release-binary` already works around it. This caller did not.

**The fix, in the org's proven shape:**

| event | behaviour |
|---|---|
| `workflow_run` (tag-on-merge, success) | publish the newest `v*` tag as this repo's base image — image tag == git tag without the `v` |
| `pull_request` / `workflow_dispatch` | **unchanged**: build only (`push=false`), the reusable derives its own `ci-<sha>` |

A small `tag` job resolves the tag and hands it to the reusable's existing `tag:` input; `push` is true only for the `workflow_run` arm, so nothing else changes behaviour.

## How tested

**The tag picker, executed live against this repo:**

```console
$ git ls-remote --tags --refs https://github.com/opencharly/pod-crabbox 'v*' \
    | sed 's#.*refs/tags/##' | sort -V | tail -1
v2026.307.1759
→ image tag 2026.307.1759
```

`sort -V`, never `sort -u`: CalVer components are not zero-padded, so a lexical sort picks the wrong tag — a fact this programme has hit before.

**The workflow parses and has the shape intended:**

```console
$ python3 -c "import yaml; d=yaml.safe_load(open('.github/workflows/image.yml')); print(...)"
YAML OK; on= ['workflow_run', 'pull_request', 'workflow_dispatch']
jobs: ['tag', 'image']
image if: github.event_name != 'workflow_run' || needs.tag.outputs.tag != ''
```

**The discriminating proof is the next `workflow_run` on this repo after merge** — the first tag-on-merge completion must produce an `image` run with `event=workflow_run` and a published digest. **That is not claimed here**; it cannot run before this lands.

**Not claimed:** that the image publishes on merge. Only that the trigger can now fire, and that the tag it will publish is the newest `v*`.
